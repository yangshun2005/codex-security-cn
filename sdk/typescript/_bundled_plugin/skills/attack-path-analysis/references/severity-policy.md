# 严重性与策略指南

在攻击路径事实、可达性和反证确立之后，使用本指南。

-- 严重性/关键性重新评级的考量 --
- 对于 `高` 及以上级别，其影响必须具有实质性的安全相关性（例如：账户接管、认证绕过、有意义的权限提升、重大敏感数据泄露/窃取、可信的远程代码执行，或类似严重的入侵），而不仅仅是错误或异常行为。
- 要使发现保持 `高` 或 `严重` 级别，其利用路径和影响应足够清晰，以至于专业安全审查员无需长篇的推测性论证即可为其辩护。
- **不要**仅仅因为普通代码错误是错误或扫描器将其标记为高/严重安全问题，就将其视为高/严重安全问题。
- **不要**基于牵强、高度推测或仅限边缘情况的利用故事来维持 `严重` 级别，除非威胁模型明确支持这些条件。严重级别要求立即关注，暗示存在迫在眉睫的威胁。
- **不要**为奇怪的配置或异常的代码库行为维持 `高`/`严重` 级别，除非有明确证据表明范围内的攻击者可以实际利用它们产生重大影响。
- **不要**依赖不寻常的操作员错误、仅限内部访问或攻击者无法到达的代码路径来证明严重的外部影响，除非仓库威胁模型表明这些行为者/路径在范围内。
- 如果问题是一个真实的错误，但并非真正的安全漏洞，则将其严重性分类为 `忽略`（或者，如果必须，`低`）。
- 如果实际上可以证明根本不存在错误（描述完全错误或虚构，并且您确实获得了证明其如此的证据），则将其严重性标记为 `忽略` 以标记误报。

以下非详尽示例列出了在代码和上下文中得到证实后通常支持 `严重` 级别的漏洞：
- 可信的远程代码执行或任意代码执行（命令注入、本地文件包含执行、琐碎的内存破坏利用等）。需要实际证明攻击者输入从范围内的攻击面导致了此问题。
- 具有重大已证实影响的真实跨站脚本（例如会话/令牌窃取、账户入侵、特权操作执行等）。
- 账户接管或强认证绕过，尤其是零点击。
- 缺少授权检查 / 授权绕过 / 租户边界突破（琐碎的 IDOR、易于交换组织或使用无授权的 ID 等）。
- 具有现实攻击者访问权限的严重敏感数据泄露（本地文件包含、路径遍历、文件下载范围界定不当、未经授权访问数据、琐碎的侧信道）（证明攻击者可以读取机密、个人身份信息、签名密钥、凭据存储、私钥、机密或高度机密信息（如模型权重等））。
- 具有已知利用模式且利用难度低的琐碎内存破坏利用。
- SQL 或其他数据库或查询注入，具有从范围内攻击面到攻击者输入的清晰路径证明以及注入的影响（泄露敏感数据、插入危险记录）。
- 破坏预期隔离边界的沙箱、容器、虚拟机、浏览器或解释器逃逸。
- 服务器端模板注入导致远程代码执行或机密泄露，并实际证明模板库可被利用来实现此目的（远程代码执行逃逸或范围内的机密/凭据），并且可从范围内的攻击面到达。
- 在可执行文件、启动、配置或固件路径中进行任意文件写入，具有现实的持久性或代码执行路径。需要证明攻击者可以从范围内的攻击面实际触发此操作。
- 允许大规模不可逆或广泛完整性破坏的逻辑缺陷，例如未经身份验证删除其他用户的数据、跨租户篡改敏感记录，或未经授权修改安全关键配置，当影响被清晰证明且严重到等同于入侵时；当有实际证据表明此逻辑可从范围内的攻击面被利用时。
- 其他未列出的、遵循此严重级别和影响的错误；并有实际证据表明这些错误可从范围内的攻击面到达。

以下非详尽示例列出了在代码和上下文中得到证实后通常支持 `高` 级别的漏洞：
- 服务器端请求伪造，有实际证据表明（1）攻击者可以从范围内的攻击面控制被请求的 URL（绕过相关保护），并且（2）可能存在其他可到达的本地/局域网/云服务以显示实际影响。除非有明确证据表明其危险，否则报告 webhook 时要小心；但当攻击者控制的目标仍可到达内部、元数据、文件支持、重定向或副作用目标时，不要将产品预期的 webhook/下载/回调功能或可选的操作员允许/拒绝列表视为抑制证据。
- 可利用的内存破坏，具有清晰、重大的影响或易于利用。
- 泄露不太敏感的用户数据或源代码的任意文件读取（如果您有实际证据表明其泄露了环境机密，则为严重级别）。
- 在可执行文件、启动、配置或固件路径中进行任意文件写入，具有现实的持久性或代码执行路径。
- 跨站请求伪造，当它启用重要的状态更改操作（如凭据更改、权限更改、支付/计费更改或安全设置更改）且受害者交互现实时。评估实际的浏览器请求行为、凭据附加、Cookie 策略、预检要求、服务器解析和有效的反 CSRF 控制；单独的 HTTP 方法或 JSON 内容类型不是绝对防御。
- 硬编码或默认凭据有效、可到达并提供有意义的访问权限，足以证明 `高` 级别，即使该访问权限不够广泛或权限不足以上升至 `严重` 级别。
- 允许签名伪造、令牌伪造、可信工件伪造、安全通道绕过或解密高度敏感数据的加密失败，从而直接促成入侵，并有实际证据表明这些攻击是可行的，并且可以从范围内的攻击面执行。
- 供应链或更新渠道入侵，允许将恶意代码或恶意可信工件交付给用户、服务器、代理或端点，包括签名绕过或包源替换并产生实际影响。这应侧重于实际的供应链风险和 CI 操作风险，而不仅仅是“npm 是否报告过时的包”。
- 授权绕过、IDOR 或权限提升，暴露或修改有意义的敏感数据或特权功能，但范围更窄，限于较小的对象集，限于同一租户边界内，或以其他方式不如上述严重情况具有灾难性。
- XXE，有明确证据表明攻击者可以通过范围内的攻击面控制 XML 文档，并且 XML 引擎易受 XXE 攻击。
- 其他未列出的、遵循此高严重级别和影响的错误；并有实际证据表明这些错误可从范围内的攻击面到达。
- 危险的上传/文件处理问题，启用存储的活动内容、可信来源脚本执行或有意义的内容类型混淆并产生实际安全影响；并有实际证据表明上传和访问都可通过范围内的攻击面到达。
- 反序列化、SSTI、插件滥用、宏/模板滥用或解释器滥用，其中危险原语清晰可到达且有影响，但代码执行或入侵尚未完全证明达到严重级别所需的标准。

通常将可能为 `高` 的发现推高至 `严重` 级别的强因素：
- 可从互联网或其他广泛的范围内表面进行未认证或近乎未认证的访问。
- 零点击或极低摩擦的利用。
- 跨租户/跨边界影响，而非同用户或同租户影响。
- 直接入侵签名、身份、控制平面或云凭据。
- 现实的持久性、大规模利用、蠕虫化或同时入侵许多受害者。
- 清晰证明代码执行、完全账户接管或核心机密访问，而不仅仅是可能的路径。

在没有非常强的证据表明其导致上述漏洞类别的情况下，通常不应保持 `高`/`严重` 级别的示例：
- 一般性正确性/可靠性错误。
- 攻击者价值不明确的奇怪边缘情况。
- 低影响信息泄露。
- 仅限内部缺陷且攻击者无法到达。
- 报告孤立地显示了一个错误类别，但没有现实的利用路径。
- 该问题要求攻击者已经拥有特权、管理员、root、控制台、shell 或代码执行访问权限。
- “如果与许多假设结合可能重要”的论点。
- 无受害者或无明显边界跨越的自 XSS，或其实际来源、浏览器可达性和影响不足以证明 `高`/`严重` 级别的 XSS。`alert` 证明演示了 JavaScript 执行，并不是反对反射型 XSS 的证据。
- SQLi 或其他注入声明，没有演示攻击者控制、没有显示接收器可达性，或仅推测性影响。
- 对低影响操作、外观性操作、注销、偏好设置或需要不现实受害者行为的操作进行 CSRF。
- 开放重定向、点击劫持、用户枚举、速率限制弱点、横幅泄露、版本披露、目录列表、堆栈跟踪、内部主机名或基本错误消息泄露，除非它们被证明是严重利用链的一部分。
- 理论上的、无法从范围内输入触发的，或在目标环境中不可合理利用的内存破坏。
- 缺少标头、Cookie 标志、CSP 弱点、TLS 观察或加密卫生问题，而没有具体的利用路径和有意义的已证明影响。
- 实际上表示“如果与其他东西结合可能危险”但未展示其他东西的报告。
- 瞬态、单用户、自目标、易于缓解、需要不成比例攻击者资源或不会产生严重且现实的业务/安全影响的拒绝服务。
- 需要已拥有与受害者相同权限或仅暴露琐碎元数据的授权发现。
- 已经需要 admin/root/shell 访问权限的错误，除非权限提升增量本身是被报告的问题。
- 仅限于公共文件、低敏感度文件或没有现实安全后果的源代码片段的任意文件读取。

高/严重级别接受检查清单（除非威胁模型强烈证明例外，否则所有项都应成立）：
- 范围内组件。
- 现实攻击者。
- 合理的范围内攻击面。
- 可信的利用路径（不仅仅是推测）。
- 重大安全影响。
- 在严肃的审计或漏洞赏金分类中，很可能会被一家声誉攸关的主要审计公司接受为 `高`/`严重`（而非信息性/低）。

## 严重性与策略检查清单

仅在范围、可达性和反证确立后应用严重性调整。不要在此重新开启发现过程。

从候选发现的原始严重性假设开始，然后使用此阶段基于仓库证据的事实进行调整。

严重性调整指南：

- 仅当攻击路径、可达性和影响都足够清晰，以至于该发现需要立即关注时，才保持 `严重` 级别。
- 仅当存在现实的范围内攻击者路径和重大安全影响且无需冗长的推测链时，才保持 `高` 级别。
- 当路径是真实的但限于较窄的对象、同租户影响、仅限内部表面或其他实质性限制条件时，降级。
- 当路径仅限 localhost、仅限自身、高度受限、依赖不现实的先决条件，或已需要特权访问（除非权限提升增量是问题所在）时，降低严重性。
- 单独的危险接收器、可怕的错误类别或敏感代码区域不足以保持高严重性。
- 如果问题是一个真实的错误，但在上下文中不能有意义地作为安全问题报告，则将最终策略决策设置为 `忽略`。
- 不要仅仅因为其影响或可能性为 `低` 而丢弃原本可报告的发现；而是降低其严重性。

最终策略调整指南：

- 首先应用硬性抑制：
  - 仅限自身影响 -> `忽略`
  - 无法实现或高度不现实的先决条件 -> `忽略`
  - 仅限特权、仅限操作员、仅限开发人员、仅限物理访问或受保护写入路径的先决条件 -> `忽略`，除非权限提升增量本身是问题所在。
- 然后使用已确定的网络范围权衡可能性：
  - 当攻击者位置现实且在范围内时，`远程` 通常支持高可能性。
  - 除非证据更强或更弱，`本地网络` 通常支持中等可能性。
  - 除非较低特权攻击者可以现实地到达该监听器，`本地主机` 通常支持低可能性。
  - `无` 不会基于暴露增加可能性。
- 然后使用现有事实决定可报告性：
  - 如果仓库证据未建立现实的较低特权范围内攻击者路径，则设置 `忽略`。
  - 如果路径仅限内部、仅限开发人员、仅限操作员、仅限 localhost、特权本地，或在上下文中无法有意义地报告，则设置 `忽略`。

当仓库证据仍显示真实产品或生产服务工作流中存在有意义的授权、信任边界、身份或安全控制回归时，不要仅因为表面是私有或内部的而抑制。在这些情况下，内部暴露通常应降低可能性或置信度，而不是强制 `忽略`。

在适当时，使用缺失的部署或入口证据来降低置信度或保持字段未知；不要仅基于此自动否定一个原本证据充分的发现。

严重性校准和最终策略调整矩阵：

- `影响=高`：
  - `可能性=高` -> 仅当满足上述严重标准时 `严重`；否则 `高`
  - `可能性=中` -> `中`
  - `可能性=低` -> `低`
  - `可能性=忽略` -> `忽略`
  - `可能性=未知` -> `中`
- `影响=中`：
  - `可能性=高` -> `中`
  - `可能性=中` -> `低`
  - `可能性=低` -> `低`
  - `可能性=忽略` -> `忽略`
  - `可能性=未知` -> `低`
- `影响=低`：
  - `可能性=高` -> `低`
  - `可能性=中` -> `低`
  - `可能性=低` -> `低`
  - `可能性=忽略` -> `忽略`
  - `可能性=未知` -> `低`
- `影响=忽略`：
  - 所有可能性 -> `忽略`
- `影响=未知`：
  - `可能性=高` -> `中`
  - `可能性=中` -> `低`
  - `可能性=低` -> `低`
  - `可能性=忽略` -> `忽略`
  - `可能性=未知` -> `低`

最终严重性后的优先级映射：

- `严重` -> `P0`
- `高` -> `P1`
- `中` -> `P2`
- `低` -> `P3`

在最终策略调整通过确定最终可报告严重性后，使用此映射。不要为最终策略决策为 `忽略` 的发现分配优先级。

一旦事实确定，机械地使用严重性校准和最终策略调整矩阵。之后不要从头重新论证严重性。
