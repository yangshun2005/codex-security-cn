# 攻击路径事实指南

在严重性校准之前，请在攻击路径分析期间使用本指南。

## 攻击路径事实

在分析过程中，应以结构化形式收集攻击路径事实，但最终报告应将其以 Markdown 形式呈现在诸如 `### 攻击路径事实` 或类似清晰标题的部分下。

该呈现的事实部分应明确涵盖：

- 假设
- 上下文：
  - 影响是仅限自身还是跨越了有意义的边界
  - 支持该结论的仓库证据
- 根据威胁模型的范围内状态：
  - 组件是否在范围内
  - 推理依据
- 暴露面：
  - 表面是否为公开
  - 当存在仓库证据时的端口、入口和负载均衡器类型
  - 证据
- 身份：
  - 服务账户或托管身份（如果存在）
  - 有效权限
- 跨边界行为：
  - 是否实际验证了边界跨越
  - 证据链
- 攻击向量：
  - `远程`、`本地网络`、`本地主机`、`无` 或 `未知`
  - 证据
- 前置条件：
  - 攻击者需要什么
  - 这些前置条件是合理、不太可能、无法实现还是未知
  - 证据
- 攻击者输入控制：
  - 攻击者控制是“是”、“合理”、“否”还是“未知”
  - 证据
- 类别
- 已存在的缓解措施
- 认证范围：
  - 路径是公开、仅内部、仅管理员还是未知
  - 证据
- 影响面：
  - 构建、运行时、数据、身份、网络或其他
  - 证据
- 目标范围：
  - 单一服务、基础镜像、集群或未知
  - 证据
- 机密引用：
  - 机密类型和引用链（如果存在）
- 反证：
  - 对可报告性驱动事实最有力的冲突性仓库证据
  - 该证据为何具有或不具有决定性
- 盲点
- 控制措施
- 置信度

建议将这些事实转化为易读的要点或简短标注段落，而不是暴露原始模式转储。最终报告应使范围和可报告性事实易于检查，包括：

- 根据威胁模型，发现是否在范围内
- 表面是公开、内部、仅管理员、仅本地主机还是未知
- 存在哪些攻击者控制的输入
- 攻击者需要哪些前置条件以及它们是否可实现
- 是否跨越了真正的信任边界
- 涉及哪些身份、权限或机密
- 已存在哪些缓解措施和控制措施
- 最有力的仓库反证是什么
- 仍存在哪些盲点或残余不确定性

同时确保呈现的报告继续包含：

- 以编号攻击者步骤形式呈现的事实性攻击路径
- 可达性和范围判定逻辑
- 最有力的冲突性仓库证据
- 抑制后的最终策略决定
- 影响和可能性背后的推理依据
