# 安全攻击路径分析

## 目标

将已验证或仍可能成立的发现转化为明确的攻击者故事、结构化的攻击路径分析事实、严重性校准，以及基于威胁模型的最终可报告性决策。

## 工件解析

本技能中的路径引用是此阶段的默认位置。
如果用户明确提供了所需输入或输出的不同路径，请使用用户提供的路径，而非本技能中引用的相应默认路径。
如果所需输入仍然缺失，请停止并先向用户询问，然后再继续。
使用 `../../references/scan-artifacts.md` 中共享的扫描工件路径约定。

标准扫描和深度扫描工作器在其常规标准扫描工作流程中评估攻击路径；两者均不调用此独立阶段技能。

### 紧凑型工作台支持的差异模式

当工作台支持的 `$security-diff-scan` 具有 `scanId` 时，加载每次扫描的威胁模型，并使用 `list_codex_security_candidates({ scanId, cursor?, limit? })` 读取已验证的候选对象。分析每个 `reportable` 或 `deferred` 候选对象，保留所有发现和验证字段以及原始候选顺序，并通过一次 `record_candidate_attack_paths({ scanId, attackPaths: [{ candidateId, attackPath }] })` 调用提交所有决策。当没有候选对象进入此阶段时，提交 `attackPaths: []`。现有工具会原子性地更新存储的候选对象；在此紧凑差异模式下，不要创建逐条发现的报告、收据或手动候选台账。将攻击路径事实、反证、严重性校准和政策调整作为独立的推理步骤。其他扫描和独立工作流程保留其现有的工件行为。

## 工作流程

1. 从 `../../references/scan-artifacts.md` 加载每次扫描的威胁模型路径，作为仓库特定的威胁模型事实来源。从该模型和潜在发现开始。这两个输入都是此工作流程所必需的。
   - 对于仓库范围和限定路径的扫描，包括标记为 `reportable` 或 `survives: yes` 的验证闭合行，即使它们在发现过程中未被分配正式的候选编号。
2. 确定受影响的代码是否在仓库威胁模型的范围内，以及它是否属于产品表面或生产工作流程。
3. 仅使用仓库证据构建事实性的攻击路径：
   - 服务映射
   - 暴露和入口点
   - 身份、权限和信任边界
   - 秘密处理和敏感数据流
   - 可达性
   - 现有控制和缓解措施
4. 在最终确定范围或可报告性驱动事实之前，识别针对关键范围字段的最强仓库反证，并解释其为何具有或不具有决定性。
5. 根据仓库证据校准影响和可能性。
6. 使用这些事实和校准后的严重性，机械地应用单独的最后政策调整过程。
7. 明确记录最终政策决策 `ignore`；在紧凑差异模式下，保留其候选记录以覆盖范围，否则将其从存活的发现集中移除。
8. 对于持久差异扫描，在单个紧凑工具调用中为每个符合条件的候选对象提交嵌套决策。否则，保存该发现的可见攻击路径报告，并为每个候选 ID 在 `../../references/scan-artifacts.md` 的默认路径下追加一条攻击路径收据。收据必须记录候选 ID、攻击路径可报告性决策、攻击路径事实或确切证明缺口，以及该候选发现的攻击路径工件/报告引用。

## 范围和攻击路径检查清单

在最终确定攻击路径事实或政策决策之前，请使用此检查清单：

- 确定发现是否实际上是真正的安全漏洞，而不是正确性错误或误报。
- 确定受影响的代码是否属于产品表面或生产工作流程。
- 从仓库证据中映射相关服务、组件或工作流程上下文。
- 从仓库证据中建立暴露和入口点，例如监听器、入口、负载均衡器、服务端口、清单、路由或网络策略。
- 建立对路径重要的身份、权限和信任边界。
- 确定是否涉及敏感数据、秘密引用或特权控制路径。
- 确定现实中的攻击者是否能够从范围内的攻击面实际到达并使用该问题。
- 在最终确定范围和可报告性驱动字段之前，识别针对这些字段的最强仓库反证。
- 当仓库证据不完整时，降低置信度或保持字段未知；不要仅仅因为缺少部署证据而自动抑制发现。

## 反证检查清单

对于最具解释性的字段，明确询问哪些仓库证据表明相反情况，以及它为何能或不能推翻该发现：

- 根据威胁模型的范围状态
- 向量
- 认证范围
- 暴露
- 跨边界行为
- 前提条件
- 影响面

特别寻找表明路径存在以下情况的仓库证据：

- 超出范围
- 仅限内部
- 仅限管理员
- 非跨边界
- 攻击者不可达
- 不具有实际可报告性

使用 `references/severity-policy.md` 应用严重性和政策校准。

## 输出契约

在紧凑差异模式下，每个具有验证处置 `reportable` 或 `deferred` 的候选对象必须恰好接收一个嵌套攻击路径决策。记录的决策是完整阶段输出；不要同时创建叙述性报告或收据。否则，使用以下报告契约。

对于每个存活的发现，包括：

- 标题
- 候选 ID、实例键和台账行 ID（如果提供）
- 验证中的受影响行，保留标记的入口点/包装器、root_control、汇聚点和具体实现位置
- 攻击路径步骤
- 渲染的攻击路径事实
- 反证摘要和挑战
- 严重性校准
- 最终政策决策
- 足够的推理，以便后续读者理解发现为何存活或被抑制

使用 `references/attack-path-facts.md` 渲染攻击路径事实。

## 硬性规则

- 使用仓库证据和明确提供的上下文。仅在用户明确授权时访问网络；离线扫描绝不访问网络。
- 不要编造代码不支持的攻击链。
- 不要隐含候选覆盖范围。在紧凑差异模式下，为每个符合条件的候选对象记录嵌套攻击路径决策，即使最终政策决策是 `ignore` 或 `deferred`。否则，每个进入攻击路径分析的候选对象必须在其候选台账路径中留下攻击路径收据，路径来自 `../../references/scan-artifacts.md`。
- 在将已验证发现转换为攻击路径时，不要丢失确切的受影响位置。通过验证存活的仓库范围种子/root-control 行必须保留其 root-control 文件：行，即使包装器、路由或传输更容易解释。
- 不要因为相邻同族发现具有更清晰的故事而跳过可报告性验证行。要么为该确切行生成攻击路径事实，要么使用仓库反证做出明确的最终政策决策。
- 缺少公共入口证据本身不是决定性的反证。
- 将攻击路径分析、严重性校准和最终政策抑制作为独立的子阶段。
- 在事实确定后，机械地使用最终政策调整矩阵，而不是从头重新论证严重性。
- 在紧凑差异模式之外，使用该发现的攻击路径分析报告路径（来自 `../../references/scan-artifacts.md`）为每个候选发现保存最终可见报告。

-- 攻击路径考虑因素 --
- 如果证据表明攻击者可以利用该错误，则该错误很重要。
- 攻击面通常应该是可能暴露给最终用户/外部行为者（或威胁模型中明确范围内的其他行为者）的表面。
