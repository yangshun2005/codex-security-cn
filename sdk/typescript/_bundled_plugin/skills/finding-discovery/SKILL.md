# 安全发现发现

## 目标

以威胁模型为背景，调查提议的代码或代码变更中技术上合理的安全漏洞。

标准和深度发现工作进程遵循其独立的协调器提示；它们不调用此技能。对于明确的独立仓库发现请求，直接将下面的相关检查清单应用于已授权的当前源代码，而不运行仅差异工作流或启动另一次扫描。

## 工件解析

本技能中的路径引用是此阶段的默认位置。
如果用户明确提供了必需输入或输出的不同路径，请使用用户提供的路径，而不是本技能中引用的相应默认路径。
如果必需的输入仍然缺失，请停止并向用户询问后再继续。
使用 `../../references/scan-artifacts.md` 中的共享扫描工件路径约定。

## SECURITY.md 指导门

在检查每个源文件之前，阅读 `../../references/security-guidance.md` 并解决适用的策略。委托的文件审查工作进程在阅读其分配的源文件之前也必须这样做。

### 紧凑差异工作流

当正在运行的差异扫描已经通过 `list_codex_security_review_items` 提供其文件清单时，直接审查该清单，并使用 `record_codex_security_discovery_candidates` 一次性记录所有候选。不要生成排名工作列表、每个发现的分类账、发现回执或发现报告。跳过下面的旧工作流和工件要求。

### 代码差异工作流
对于没有现有紧凑清单的针对性代码差异：

- 阅读 `../security-scan/references/scan-artifacts-and-ledger.md`。
- 使用 `<python_command> <plugin_dir>/scripts/generate_rank_input.py make-diff-rank-input --repo <repo_root> --base <base> --mode revisions --head <head> --out <discovery_dir>/rank_input.jsonl` 为 PR、提交和分支差异确定性地从更改的类似源文件生成 `rank_input.jsonl`，或使用 `<python_command> <plugin_dir>/scripts/generate_rank_input.py make-diff-rank-input --repo <repo_root> --base <base> --mode local-patch --out <discovery_dir>/rank_input.jsonl` 为本地补丁生成。
- 使用 `<python_command> <plugin_dir>/scripts/generate_rank_input.py copy-deep-review-input --rank-input <discovery_dir>/rank_input.jsonl --out <discovery_dir>/deep_review_input.jsonl` 将每个差异行复制到 `deep_review_input.jsonl`。差异扫描在深度审查前不排名或丢弃更改的文件。
- 仅当仓库证据显示需要时，添加直接支持文件以理解更改的安全行为。不要使用它们来扩大到无关的仓库范围枚举。
- 使用共享的范围文件审查规则深度审查 `deep_review_input.jsonl` 中的每个文件。
- 保持锚定在更改的代码和直接支持文件上。未更改的兄弟文件是上下文或阴性对照，除非差异新触及它们、削弱其共享控制或更改它们依赖的共享接收器/辅助函数。
- 当差异太大而无法作为一次父代理传递可信地审查时，在已解决的扫描授权下使用文件审查子代理（如果可用），并遵循 `../security-scan/references/scan-artifacts-and-ledger.md#scoped-deep-review` 中的共享范围深度审查规则。

## 发现检查清单

使用此检查清单保持发现的具体性，而不将其变成验证或攻击路径分析：

- 在决定任何事情之前，使用工具检查更改的文件及其依赖的最少支持文件。
- 将提交消息和标题视为可能不完整或误导；更信任实际代码路径而不是叙述。
- 充分跟踪整个更改的代码链，以了解差异如何影响授权、信任边界、危险接收器或安全控制。
- 仅当多个不同的发现家族来自不同的根本原因时，才优先考虑它们；不要将一个 Issue 拆分为表面变体，但保持独立可到达的实例作为单独的候选条目。
- 当差异更改共享辅助函数、守卫、路由模式、模板模式或接收器包装器时，扩展到更改代码直接影响的兄弟调用点，并保持每个易受攻击的实例可寻址。
- 寻找由更改引入或使其可到达的攻击者控制输入、破坏的强制或危险接收器。
- 保持锚定在差异及其依赖的支持文件上，而不是漂移到无关的仓库扫描中。
- 对于顾问种子仓库范围和范围路径扫描，保持任何提供的顾问行 ID、确切文件、行、源、接收器或破坏控制提示在候选分类账中可见。相邻的相同 CWE 发现可以是额外的候选，但除非它覆盖相同的易受攻击控制和效果，否则不满足种子行。
- 当文件具有单独的线路级源/接收器/控制证据时，不要将许多易受攻击的文件分组在一个候选下。
- 当危险接收器有多个调用点时，枚举每个调用点及其自己的源和最近的控制。
- 当重复的模板、查询构建器、解析器操作、认证/对象端点或共享辅助函数调用者独立可到达时，保持每个易受攻击的文件和接收器/控制行作为自己的候选实例，即使最终报告后来分组相关散文。
- 当源/接收器证据跨越包装器进入共享接收器/控制辅助函数时，在候选中包含两个位置，以便验证可以在不丢失根本易受攻击行的情况下测试可到达性。
- 当具体操作、策略、转换器、验证器或处理程序子类选择攻击者控制的操作语义并委托给共享的破坏控制或接收器时，将该子类方法或构造函数作为受影响的候选位置与共享辅助函数一起包含。不要仅用抽象基类或共享辅助函数替换它。
- 如果候选声明说共享解析器、加载器、评估器、认证守卫或操作家族影响“所有”、“每个”或“任何”具体实现，枚举使该声明成立的具体实现。不要仅在散文中留下具体的易受攻击类。
- 当广泛的候选桶命名整个操作家族，如“所有 SQL 触发器变体”、“所有反序列化变体”、“所有路径遍历辅助函数”、“所有 SSRF 模式”、“所有生成的框架适配器”或“所有未认证的变更端点”时，在将集合交给验证之前，将其扩展为由具体导出函数、路由分支、接收器语句、API 模式、解析器/反序列化器变体或受保护操作键控的子候选。
- 如果一个路由或辅助函数暴露同一家族中的多个危险操作，如 `execute`/`executemany`/`executescript`、`pickle.load`/`pickle.loads`/`yaml.load`/`yaml.load_all`、分离的路径/文件辅助方法、插入/选择/删除/更新查询构建器，或创建/删除/重置/管理员/作业操作而没有认证，当攻击者可以独立触发它们时，保持这些操作作为单独的候选实例。
- 将共享或生成的包装器视为可到达性证据，而不是折叠子接收器变体的理由。包装器可以是共享的受影响位置，但每个独立的接收器、控制或受保护操作仍然需要自己的候选 ID。
- 当扫描上下文或证据种子特定边界包、类家族或漏洞家族时，保持该种子行打开，直到该确切包或类家族被关闭。附近的同家族发现是支持上下文，而不是种子根控制的替代品。
- 当提供 CVE、GHSA、顾问、发布、Issue 或包版本上下文时，使用任何顾问种子研究工件作为发现输入。将种子研究的文件/函数/类/块保留为分类账行，直到本地代码证据将它们关闭为可报告、抑制、不适用或延迟。
- 当 CVE/顾问上下文具有通用或无用的类别时，不要直接回退到广泛的热点发现。首先从顾问/修复/发布/安全测试源（如果可用）推导种子候选列表；如果不可用，则对项目特定的协议、解析器、验证器、实用程序和版本/比较辅助函数以及 CVE/顾问术语运行本地回归种子传递。
- 如果发现打开或 grep 种子目标文件、类、包或块，为其创建显式关闭行。不要将确切种子仅留在工具输出、后台上下文或抑制候选散文中。如果更广泛的兄弟发现共享相同的证明元组，将种子锚文件/行保留为受影响位置；否则单独关闭种子行。
- 对于顾问引导的行，不要仅因为相邻 Issue 更容易利用或验证而用相邻热点替换确切种子构造。保持种子行打开，直到本地仓库证据独立支持或反驳相同的源、破坏控制和影响元组。
- 对于共享反序列化、类解析、模板和认证控制，当下游传输或调用者证明可到达性时，将解析器/过滤器/允许列表/拒绝列表/守卫行视为候选位置。如果破坏控制可重用，不要仅锚定在更戏剧性的传输上。
- 对于反序列化和对象构造家族，枚举由解析器或序列化配置注册的具体编解码器、反序列化器、转换器和容器处理程序，包括数组、集合、映射、Bean、枚举、可抛出和通用对象处理程序。当该编解码器递归调用攻击者控制数据上的解析、类型解析、转换或对象构造时，顶级解析器/配置发现不会关闭具体编解码器行。
- 对于文件格式对象模型，枚举转换或遍历攻击者控制文档结构的原始/容器辅助方法，包括 `to*Array`、`get*`、`getObject`、数字转换、`parse*`、迭代器、`size`、未检查转换和分配循环。当畸形文档可以触发类型混淆、异常、无界遍历或内存/CPU 耗尽时，将这些辅助函数视为候选根控制。
- 如果仓库范围工作列表或覆盖分类账识别不受信任格式的中心对象模型包，在关闭解析器家族之前，将该包的数组、字典、节点、集合和原始转换辅助函数作为发现行包含。相邻包中的解析器、过滤器或编解码器发现不会关闭核心对象模型中未检查的转换辅助函数。
- 对象模型辅助函数扫描首先创建强制发现行，而不是自动可报告发现。仅当畸形或对抗性输入可能到达辅助函数，并且缺失的类型、大小、形状、递归、数字或转换守卫可能导致崩溃、拒绝服务、解析器混淆、授权绕过或另一个具体安全影响时，才提升它们。
- 当不受信任的远程、协议、文档、存档或包输入可以到达缺失的守卫并中止服务、请求工作进程、解析器流水线或安全协商时，不要将确定性解析器/辅助函数崩溃抑制为仅仅是健壮性问题。抑制需要精确的包含证据，如调用者侧恢复、等同于缺失守卫的输入预验证或非仅安全边界。
- 对于结构化补丁/编辑/应用 API，如 JSON Patch、Graph Patch、文档编辑或配置变更，枚举具体的请求选择操作，如添加、删除、替换、移动、复制和测试。当它们馈入共享评估器或绑定器时，保持操作特定的路径转换、数组追加处理、通配符选择或对象绑定行候选可见。
- 在具体操作类中，检查专门的辅助方法，而不仅仅是顶层 `perform`、`handle` 或 `apply` 覆盖。如果操作特定的辅助函数在委托给共享评估器或绑定器之前拆分、过滤、规范化或重建攻击者控制的路径，使用该辅助函数行作为候选根控制。
- 当具体操作具有特殊情况分支，如追加、通配符、回退、复制/移动 `from`、默认值或类型解析路径时，当它们绕过或缩小共享验证器时，保持分支谓词和分支本地转换行作为受影响位置。共享辅助函数发现不会关闭分支特定的根控制。
- 当类过滤器、允许列表、拒绝列表、黑名单、白名单或解析器逻辑在核心、服务器、客户端、远程处理、插件或导入包中重复时，当它们实现相同的破坏控制时，将运行时/导出等效项作为候选位置包含。传输调用点证明可到达性，但不替换可重用的解析器实现。
- 在框架或库扫描中，当存储的客户端、租户、应用程序、身份提供者、异常或导入配置值稍后被渲染、评估、解析或用于授权，并且实例具有从应用程序、租户、身份提供者、导入或其他边界的合理运行时路径时，它们是跨边界输入。不要仅因为写入者在当前仓库之外而抑制，除非仓库证据证明该值仅对正常部署是可信的。
- 对于 SQL/NoSQL/LDAP/XPath 和类似查询 API，不要仅因为端点已经接受用户控制的数据、操作是插入/更新或稍后的业务检查似乎限制最终应用程序效果而抑制候选。如果攻击者控制的输入通过合理的运行时路径到达查询语法或选择器运算符，将候选带到验证，并记录稍后的检查作为可能的反证据。
- 不要仅因为共享路由或辅助函数而将分离的高影响证明元组折叠为一个候选。当接收器、最近控制或影响不同时，拆分命令执行、SSRF、路径/文件影响、XML/解析器行为、XSS/模板执行和授权/状态更改影响。
- 对于出站请求表面，如 `downloadFrom`、URL 导入器、webhook/回调客户端、预览/渲染获取器和重定向跟随 HTTP 客户端，枚举每个攻击者控制的目标源及其最近的允许/拒绝/过滤/重定向控制。不要因为获取/回调是预期功能、过滤器默认可选或为空、或兄弟路由发现更响亮的文件/路径 Issue 而抑制 SSRF；当用户输入可以选择目标且硬边界不完整、操作员配置或仅请求前时，保持网络行。
- 在 XML/解析器/反序列化器表面，独立枚举默认解析器工厂、转换器、验证器、转换器、反序列化/解析调用和处理程序入口点。安全的兄弟解析器路径是该兄弟的阴性对照，而不是不同默认工厂或转换器的抑制证据。
- 对于命令/操作运行器，在关闭命令注入覆盖之前，枚举每个攻击者可控制的参数类型和执行模式。将类型安全映射、不安全类型拒绝列表、模板替换、shell 包装、直接执行分支、webhook/API 参数摄取和仅前端小部件约束视为单独的控制。覆盖 `raw`、`url` 或 `email` 的拒绝列表不会关闭 `password`、`checkbox`、`confirmation`、选择或其他 nil/no-op 类型检查分支，这些分支仍然可以渲染到 shell 命令中。
- 对于 XML 解析器和转换器候选，当加固是尽力而为、失败开放或不完整时，包含功能设置和解析器行。单独的 `FEATURE_SECURE_PROCESSING`、吞下/记录的 `setFeature` 失败或安全默认解析器不会抑制调用者提供的解析器工厂/读取器或从不受信任数据创建 SAX/DOM/StAX/Transformer 源的转换器路径。
- 对于资源服务和静态文件路径，包含决定攻击者选择的路径是否被允许的允许列表、匹配器、规范化、URL 解码和资源选择行。不要用更安全的兄弟处理程序替换易受攻击的旧版或包 API 处理程序。对于恢复/导入/导出、备份、管理员或登录命名路由，在假设需要认证之前，还验证确切全局中间件和装饰器语义；可选或有条件的登录包装器在启用认证配置缺失时保持路由匿名。
- 对于路径敏感文件系统家族，枚举恢复/导入/导出、备份/恢复、存档提取、文件复制/移动、下载/打开和密钥/配置获取辅助函数的具体导出操作。为每个独立可到达的操作保持解码、连接、规范化、规范化、剥离前缀、扩展检查和目标选择行候选可见。
- 对于存档提取和恢复/导入流程，保持存档成员名称、目标连接、包含检查和提取/写入调用作为候选根控制可见。如果提取或文件系统写入已经首先发生，不要用稍后的复制、导入、UUID/清单门或顶层文件选择步骤替换它们。标准库辅助函数规范化路径的通用声明是不够的；保持行打开，直到代码在提取或写入之前显示每个条目的精确包含，包括任何符号链接、硬链接、元数据或递归复制路径，这些路径可能稍后将攻击者控制的内容提升到导入子树中。不要要求写入逃逸整体应用/数据存储根；覆盖该根内的可信配置、对等对象目录、共享根或导入子树仍然计为文件影响。
- 当上传/存档成员行具有从解码/过滤成员名称到目标连接/写入元组的精确源时，即使运行时包复现不可用或置信度为中等，也保持它们作为候选。同一仓库中更干净的下载/打开遍历或 API/认证 Issue 不是丢弃存档成员行的理由；以校准的严重性/置信度报告存档行，或保留带有缺失证明的显式延迟分类账行。
- 当同一产品区域也有认证、秘密或配置错误时，保持路径/文件候选打开，直到其自己的证明元组关闭。不要用更响亮的相邻 Issue 替换它。
- 在框架或库扫描中，不要仅因为受影响的 API 已弃用、选择加入或记录为危险而抑制高影响候选。将其作为前提条件说明；当发布的运行时代码在受限或正常使用路径中包含可绕过的控制，并且实例具有合理的跨边界源和运行时/部署路径时，保持候选。
- 在认证/授权表面，独立于附近的凭据或配置错误，枚举读取受保护对象、触发构建/作业或变更受保护状态的公共 webhook、状态、回调和 API 端点。
- 对于有状态认证协议，包含在预认证、TLS 升级、重定向、断言或身份提供者转换后安装或重用主体、凭据、令牌、颁发者或协议状态的行。缺失重新绑定/重新认证或验证与消费不匹配是候选控制，当它们可以认证错误身份时。
- 在 SSO/SAML/联合包中，保持响应/断言验证器与通用声明授权器和服务方法授权不同。当它们决定信任或返回哪个断言时，包含断言选择、列表索引、`getDOM`、`cloneNode`、签名对象查找、主题确认、接收者、受众、目标、ACS URL 和颁发者绑定行。
