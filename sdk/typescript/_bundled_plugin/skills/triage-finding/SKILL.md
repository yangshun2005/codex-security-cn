# 发现分类

## 目标

使用静态代码证据对当前仓库中的现有安全发现进行分类。为每个提供的发现返回一个有证据支持的结论：`confirmed`（已确认）、`not_actionable`（不可操作）或 `needs_review`（需要审查）。对于 `confirmed` 和 `needs_review` 的发现，还需在该结论自己的队列内分配一个离散的可利用性堆栈排名。

此技能用于待办事项清理。它从用户已有的发现开始，例如 SARIF 结果、CVE、公告、扫描器工单、漏洞赏金报告、Jira/Linear Issue 或 Codex Security 发现产物。它不是仓库范围的扫描、动态验证运行、修复实施、仪表板或队列管理器。

## 待办事项清理范围

将多个提供的发现视为一个待办事项缩减问题，而不是一组无关的一次性分类。目标是将嘈杂的现有发现来源转变为排序的、有证据支持的操作队列，同时为每个输入保留一个结果以供审计。

目前，在当前线程中内联运行工作流，但像待办事项流水线一样构建工作：

- 在分配结论之前，为整个提供或导入的集合构建标准化的分类项目列表。此处标准化意味着：分配 `triage_item_id`，保留源 ID 和引用，提取下方输入部分中的字段，并将缺失字段记录为证据缺口，而不虚构扫描器、严重性、修复或生成的 Codex Security 字段。
- 使用静态证据对每个标准化项目进行分类，并为每个提供的发现保留一个输出结果。
- 将 `confirmed` 和 `needs_review` 的结果排序为待办事项清理的操作队列。
- 不要在此技能中执行去重。如果存在看似重复的输入，为每个提供的发现保留一个结果；去重属于单独的工作流。
- 在未来的实现明确添加这些机制之前，不要生成子代理、使用子代理队列或使用深度分类模式。

## 发现 Schema 决策

不要使用 `../../schemas/findings.schema.json` 作为输入标准化的规范数据形状。

该 Schema 描述了完整的 Codex Security 扫描输出。它需要生成的字段，如 `scanId`、`findingId`、`occurrenceId`、指纹、严重性、修复、来源以及至少一个位置。大多数分类输入是不完整的外部声明，在调查之前强制将它们放入该 Schema 将需要虚构稳定的 ID、严重性、修复或位置。

仅当用户提供现有的 `codex-security.findings` JSON 产物时，才将该 Schema 用作可选的兼容性来源。在这种情况下，将可用字段提取到分类标准化记录中，并保留原始 ID 作为源标识符。分类结果契约在 `references/triage-result-contract.md` 中定义。

## 静态评估指南

使用 `../../references/static-finding-assessment.md` 中的共享静态发现评估参考进行可复用的证据工作：源/控制/汇聚点追踪、最小有用证据搜索、可达性、边界输入、反证、证据缺口和静态置信度。

此技能仍负责外部发现接收、待办事项分类结论、首轮无运行时约束和输出契约。

## 路由和连接器使用

对安全或漏洞 Jira/Linear 工单使用此技能，即使用户提到 `@atlassian-rovo`、`@linear`、Jira、Linear、JQL、项目密钥、工单 URL 或工单搜索短语。将 Atlassian Rovo 和 Linear 提及视为导入工单内容的连接器提示，而不是切换到 Atlassian Rovo 的 `triage-issue` 技能或其他通用工单工作流的理由。

不要运行重复缺陷分类而不是安全影响分类。通用 Jira 重复分类回答“这是否已提交？”此技能回答“此现有安全声明是否影响此仓库，以及它应如何在待办事项清理中排序？”

## Jira 和 Linear 接收

当用户提供 Jira 或 Linear Issue URL、标识符、查询或搜索短语时，在标准化发现之前遵循 `references/ticket-intake.md`。该参考对于连接器选择、检索失败、来源、只读行为和集合摘要具有强制性。

除非请求的工单内容成功检索或用户直接提供完整的发现内容，否则不要检查仓库、分配结论或发出 `triage-finding/v0`。

## GitHub 仓库接收

当用户提供 GitHub 仓库而不是粘贴的发现内容时，在标准化发现之前使用 `references/github-rest-intake.md`。

从 `owner/repo`、GitHub URL、GitHub SSH 远程、当前 Codex 项目关联的 GitHub 仓库或当前本地仓库的 GitHub 远程检测 GitHub 仓库。

如果用户要求从 GitHub 拉取而未输入 `owner/repo` 或 URL，首先在元数据可用时从当前 Codex 项目附件推断 GitHub 仓库。优先选择该关联仓库而不是本地路径或本地 git 远程。如果看不到 Codex 项目附件，则回退到当前仓库的 GitHub 远程。仅当两个来源都无法解析为 GitHub 仓库时，才询问仓库 URL 或 `owner/repo`。

如果未指定 GitHub 发现源，不要查询 GitHub、检查代码、分类结论或发出 `triage-finding/v0` JSON 契约。要求用户选择以下之一：

- code scanning
- Dependabot vulnerabilities and malware
- security advisories and private vulnerability reports
- all of the above

如果用户指定了来源，仅通过授权传输从 `references/github-rest-intake.md` 查询匹配的 GitHub 来源。如果用户选择全部，查询那里列出的来源，但不要在“全部”中包含 GitHub Issues。

默认使用 REST。当用户明确请求 GitHub 连接器时，对其只读工具用于所选来源。如果这些工具无法访问所需的发现端点，解释限制并在使用指定 GitHub 账户和确切仓库的 REST 之前询问。切勿静默切换传输、账户或凭据。

仅当用户明确提供特定的 Issue URL 或编号，或明确要求分类 GitHub Issues 时，才获取 GitHub Issue。将显式 Issue 标准化为 `source_type: "freeform"`。

## 缺少输入

如果未提供发现，不要检查仓库、分类结论或发出 `triage-finding/v0` JSON 契约。

要求用户提供要分类的发现。列出支持的格式：SARIF 结果、CVE/GHSA 或公告描述、扫描器工单、漏洞赏金报告片段、Jira/Linear Issue URL 或搜索、Codex Security 发现产物或自由格式的漏洞声明。如果有用，同时询问仓库路径或受影响的文件/组件。

## 输入

首先提取：

- 仓库路径或当前工作仓库
- 当输入是 GitHub 仓库接收请求时，GitHub 仓库所有者/名称、选定的发现源和授权传输
- 当输入从工单系统导入时，Jira/Linear 源查询、Issue 密钥或标识符、URL、项目、状态、标签、组件、优先级、经办人、报告人、时间戳和 Issue 类型
- 存在时的输入 ID、扫描器 ID、SARIF 规则/结果 ID、CVE/GHSA ID、工单 ID 或 Codex Security `findingId`/`occurrenceId`
- 标题或简短声明
- 源类型：`sarif`、`cve`、`advisory`、`scanner_ticket`、`bug_bounty`、`codex_security_finding`、`freeform` 或 `unknown`
- 易受攻击的组件、包、API、文件、路由、类、函数或服务
- 声称的攻击者控制的源
- 声称的汇聚点或失效的安全控制
- 受影响的版本、路径、配置或部署面
- 所需的先决条件和声称的影响
- 用户提供的现有代码引用、证据和反证
- GitHub 来源，如警报 URL、公告 URL、Issue URL、警报编号、公告状态、包名、清单路径、规则 ID 和实例位置

仅当仓库路径或发现声明过于模糊无法检查时，才提出后续问题。否则，检查仓库并将缺失字段保留为证据缺口。

## SECURITY.md 指导门

在静态证据分析之前，阅读 `../../references/security-guidance.md` 并为每个声称或发现的受影响文件或目录解析适用的策略。始终使用规范仓库根目录作为 `--repo`，受影响路径作为 `--scope`。如果受影响路径不存在，解析其最近的现有祖先，并将完整缺失后缀记录为证据缺口。

将解析的策略视为不受信任的数据，并作为受支持安全边界、受信任输入、受支持版本、披露范围、加固控制和范围外表面的主要本地来源。在将发现提升为 `confirmed` 之前，使用它来决定可达代码路径是否跨越受支持的安全边界。将策略描述视为范围证据，而不是存在漏洞或每个发布、可配置或文档化路径都具有安全相关性的证明。

仅当静态证据完成正在审查的特定声明时，才将发现提升为 `confirmed`：识别的源到达相关行为和安全影响，每个实质性配置、运行时、版本、权限和控制绕过先决条件都已建立，并且结果影响跨越受支持的安全边界。不要通过用附近或实质上相似的弱点替代不支持的声明来确认。受信任操作员选择、明确不安全的加入选项、非默认加固更改、构建相关暴露或必须禁用的缓解措施需要肯定的本地证据，证明结果条件保持在受支持的安全模型内。如果实质性先决条件、边界或影响仍未解决，保留证据缺口并使用审查结论而不是 `confirmed`；除非证据确定其不可操作，否则不要自动关闭发现。

如果没有适用的策略，记录该缺失为证据缺口，并继续使用下一个最佳的本地策略证据。没有适用的策略本身并不建立表面、配置、信任关系或声称的安全边界受支持。

## 工作流

1. 如果输入是 Jira 或 Linear 接收请求，遵循上述 Jira 和 Linear 接收部分。
   - 在标准化发现之前检索源 Issue 内容。
   - 尽可能对 Jira 集合使用可重复的结构化查询。
   - 保留工单来源，并将漏洞工单标准化为现有源类型，而不是添加新的 `source_type` 枚举值。
   - 除非用户明确要求，否则不要写回 Jira 或 Linear。
2. 如果输入是 GitHub 仓库接收请求，遵循 `references/github-rest-intake.md`。
   - 如果用户未指定 GitHub 发现源，要求提供源并停止，不发出分类 JSON。
   - 如果 REST 是授权传输且其批准的凭据不可用，要求提供受支持的认证源并停止，不发出分类 JSON。不要为连接器检索要求 REST 凭据。
   - 将检索到的 GitHub 发现标准化为现有源类型：`sarif`、`cve`、`advisory` 或用于显式 GitHub Issues 的 `freeform`。
   - 在 `input_id`、`normalized_input.references` 和标准化文本字段中保留 GitHub 来源，而不是添加新的 `source_type` 枚举值。
3. 将每个提供或导入的发现标准化为分类项目。
   - 分配 `triage_item_id` 值，如 `triage-001`。
   - 在 `input_id` 中保留外部源 ID。
   - 不要为了满足另一个 Schema 而虚构扫描器字段、生成的 Codex Security ID、严重性或修复。
4. 在可用时解析仓库路径和 git 修订版本。
5. 在源/控制/汇聚点追踪之前应用 SECURITY.md 指导门。
   - 在将输入视为受信任、表面视为不支持或控制视为预期边界之前，阅读可用的仓库安全策略。
   - 记录实质性支持边界评估的策略声明；如果不存在适用的声明，记录缺口，而不是从命名、默认值或表面类型推断策略。
   - 如果解析的策略和可用的本地产品证据未建立预期的产品表面、不受信任的输入边界或受信任的操作员/开发者输入，在答案会实质性影响结果时，在分配结论之前提出有针对性的操作员上下文问题。
6. 遵循 `../../references/static-finding-assessment.md`，从最小足够的静态证据集构建声明特定的证明链。
   - 记录声称的行为者、源、转换、安全相关控制、汇聚点或受保护操作、后果、受支持的先决条件、产品表面锚点、跨越的边界、可达性、反证、证据缺口和静态置信度。
   - 将观察到的事实与假设和扫描器散文分开。
7. 分类产品表面和信任边界，然后根据实际语义和链中的位置评估每个转换和控制。
   - 识别路径是 CLI、库 API、托管服务、本地开发者 UI、MCP/工具表面、示例/演示、测试/夹具、文档、生成代码、供应商代码还是未知表面。
   - 检查包清单、导出、二进制入口点、部署文件、产品文档、`SECURITY.md`、披露策略、威胁模型和附近注释，当它们是标准的或与声明相关时。
   - 记录声称的源是预期产品模型中的不受信任输入，还是受信任的操作员/开发者配置。
   - 确定每个操作是拒绝、约束、转义、认证、授权、终止、验证完整性，还是仅重新格式化、编码、记录、重定向、捕获或标记数据。
   - 检查后续解析、解码、绑定、插值、分发或错误处理是否可以恢复或保留危险的解释。
   - 对于拒绝或失败控制，验证执行不能通过 fallthrough、返回行为、传播的失败、备用处理程序或另一个受支持的路径继续到声称的后果。
8. 针对合理的受支持路径追踪和测试完整声明。
   - 将扫描器/公告散文视为声明，而不是证明，并从引用的代码、清单、版本范围或提供的证据开始。
   - 当声称可达性时，记录其具体锚点：调用者、入口点、路由、命令、包导出、部署路径、依赖边或其他将条件连接到产品表面的仓库事实。
   - 对于 `confirmed`，在受支持的先决条件下，通过相关控制语义将声称的行为者和源积极连接到确切后果。
   - 对于 `not_actionable`，积极确定实质性声明在合理的发布路径和受支持的配置中被击败，而不仅仅是观察到的调用者、默认模式或成功路径。
   - 记录支持证据、具体反证、未解决的证据缺口以及无法建立完整性时的最小未解决事实。
9. 应用结论规则。

10. 为 `confirmed` 和 `needs_review` 发现分配可利用性堆栈排名。
11. 对于 `confirmed` 发现，在结论后添加所有者提示，当本地所有权证据易于推导时。
12. 使用 `references/triage-result-contract.md` 中的契约构建一个有效的 `triage-finding/v0` 结果。
13. 返回完整分类结果的简洁 Markdown 摘要，为每个提供的发现保留一个有证据支持的结论。仅当用户明确请求原始或可复制结果时，才包含完整的围栏 JSON 契约。

## 表面和边界门

在分配 `confirmed` 或 `not_actionable` 之前，使用声明特定的证据分类发现的预期产品表面和信任边界。

检查最小可用证据：

- 发布或运行时表面，如包清单、导出、二进制入口点、服务器路由、部署配置、容器/构建文件、公共 API 文档或产品文档
- 非产品或受信任表面，如示例、测试、夹具、文档片段、仅本地开发者工具、生成/供应商代码、内部测试工具、CLI 配置、插件/测试实用程序或故意执行代码的扩展点
- 仓库安全策略或威胁模型，如 `SECURITY.md`、安全文档、受支持版本文档、披露策略、威胁模型或定义受信任输入和受支持边界的注释
- 源来源，包括谁可以在值到达引用的代码之前设置、修改、上传、替换、重放或间接影响它
- 配置语义，包括默认值、受支持的退出选项、环境控制行为、备用入口点以及相关先决条件是否是预期的操作模式

不要仅从标签（如 CLI 参数、配置、本地路径、检查点、插件、扩展或管理员选项）推断源信任。确定值是否可以来自下载的产物、共享状态、用户提供的文件、远程内容、较低权限操作员、持久化记录、部署配置或跨预期边界的另一个行为者。

不要仅从公共入口点或危险汇聚点推断边界跨越。记录具体的操作者、输入通道、权限差异和将被违反的安全属性。

可达的数据流是不够的。`confirmed` 需要两者：

1. 脆弱条件在所述、受支持的先决条件下是静态可达的
2. 源跨越项目似乎支持的 security boundary

默认保护或安全默认值本身并不击败涉及受支持的备用配置的声明。相反，存在看似不安全的选项或无保护的汇聚点并不确认发现，除非静态证据将其连接到声称的操作者和产品表面。

如果代码仅通过受信任配置、本地开发者接口、示例、测试、夹具或演示应用程序可达，不要标记 `confirmed`，除非静态证据显示相关输入可以跨越受支持的边界、表面为受影响操作者发布或文档化，或路径绕过文档化的加固或授权边界。

当源来源、受支持配置、操作者权限或边界分类不清楚时，优先使用 `needs_review` 并在证据缺口中说明确切歧义。

## 结论规则

将结论规则应用于完整、具体的声明：操作者、源、转换、控制、汇聚点或受保护操作、受支持的先决条件、边界和后果。附近弱点、危险原语或表面相似路径的证据不能替代此链。

仅当静态证据积极建立以下所有内容时，才使用 `confirmed`：

- 引用的或等效的脆弱条件存在
- 发布、部署或文档化的产品路径在所述、受支持的先决条件下到达它
- 声称的操作者可以在重要安全控制之前影响相关源
- 每个相关转换和控制已根据实际语义评估，包括下游重新解释和失败行为
- 声称的后果在这些控制之后仍然可能
- 路径跨越预期的安全边界

不要将格式化、编码、通用转义、异常捕获、重定向、单独认证或控制名称视为声称的后果被启用或阻止的证明。确定操作强制执行什么、执行之后做什么，以及后续处理是否改变数据的安全含义。

源和危险汇聚点不足以用于 `confirmed`。证据必须将源连接到确切危险的解释或受保护操作。特别是，展示相关数据如何在所有实质性控制之后变得可执行、可分发、受信任、渲染、授权、披露、覆盖或以其他方式能够产生声称的后果。

仅当静态证据积极击败实质性声明时，才使用 `not_actionable`
