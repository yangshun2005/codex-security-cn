# 修复发现

## 目标

将当前的安全发现转化为最小且经过验证的代码更改。如果代码已经是安全的，请证明这一点并报告无需更改。

按以下顺序评判结果：

1. 当前状态被正确分类为易受攻击、已安全或未经证实
2. 任何修复都能完全关闭被破坏的安全边界
3. 合法行为和兼容性得以保留
4. 相关的仓库检查通过
5. 实现遵循仓库约定
6. 补丁仅包含满足上述属性所需的范围

切勿为了后面的属性而牺牲前面的属性。最小意味着满足所有先前属性的最小仓库原生更改，而不是最少的行数。

## 补丁契约

在编辑之前，根据仓库证据确定：

- 受影响的组件和当前的源到汇路径或损坏的控制
- 攻击者控制的输入和所需的先决条件
- 安全不变量和最窄的可行强制边界
- 需要保留或有意更改的合法行为、API、错误语义和兼容性约束，并附有支持的产品证据
- 可用的PoC、复现器、测试、证据和受影响的位置
- 最近的辅助函数和实现、错误处理及测试先例

检查仓库以填补空白。仅在存在重要的产品、安全或兼容性决策时询问用户。

## 运行时验证

在复现发现、运行测试或验证修复时，请使用以下指导：

- 在广泛设置之前完成补丁契约；从通过真实脆弱边界的最小高信号检查开始。
- 使用仓库支持的设置命令。保持修复工作有界，以免取代路径分析、修补或重点验证。
- 不要仅仅因为命令运行缓慢就停止它。首先检查进程状态、日志、产物或资源使用情况。
- 如果运行时验证仍然不可用，请使用保留真实集成边界的最强定向静态或基于测试工具的产物。不要用移除受保护行为的简化测试工具替代。将每个未运行的检查记录为未知。

## 工作流程

1. 重新验证并界定发现范围。
   - 检查仓库说明、受影响代码、直接调用者，以及仅需证明脆弱路径的上下文。
   - 在当前检出中建立具体的可达性；通用弱点标签、文件锚点和看似可疑的代码不是证据。
   - 如果在有界调查后无法显示相同的被破坏安全边界，不要修补相邻弱点或添加推测性深度防御。当证据显示路径已经安全时返回`no_change`；否则返回`blocked`并附上缺失的证明。
   - 完成补丁契约并检查相关的辅助函数、控制以及实现和测试先例。
2. 在可行的情况下，在修复前复现或编码问题。
   - 优先选择失败的回归测试、单元测试、集成测试、属性测试或真实接口复现。
   - 在实现之前，通过同一边界捕获恶意条件和至少一个合法控制。
   - 仅在不安全行为测试安全、确定且适合仓库时保留。否则使用最强的可重复验证产物并记录差距。
   - 如果在任何代码更改之前问题不再复现，调查是否已修复并保留验证证据。
3. 选择补丁策略。
   - 确定窄幅战术更改能否在保留补丁契约的同时关闭边界。
   - 仅当窄幅选项无法在不破坏受支持行为的情况下关闭边界时，才考虑更广泛的修复。仅在仓库或产品证据支持该缓解措施时，才移除或禁用功能。
   - 如果唯一完整的修复需要对产品策略、公共API兼容性或跨子系统所有权做出未解决的决策，返回`blocked`并附上选项、安全权衡以及可能的负责人或代码所有者（如果有）。
   - 使用附近的变体测试所选边界。单独报告无关的兄弟发现或长期架构工作，而不是扩大此补丁。
4. 实施修复及其证明。
   - 做出完全执行不变量所需的最小仓库原生更改。
   - 优先使用现有辅助函数和抽象。保留API、合法输入和错误语义，除非安全契约要求更改。
   - 明确处理不安全状态；不要静默接受、截断或重新解释它。
   - 避免无关的重构，并保留候选补丁之外的用户更改。
   - 添加针对脆弱行为失败并在修复后通过的聚焦回归覆盖。
   - 包含合法控制的正面覆盖。在证明不变量的最低级别测试，并在可行时通过真实接口测试。
5. 按顺序验证。
   - **适用性和可构建性**：检查最终差异是否有无关更改，然后运行最窄的相关语法、导入、构建、类型或聚焦测试检查。
   - **安全关闭**：重新运行原始PoC、触发器或最强的漏洞利用检查。在修补代码中重新追踪源到汇或损坏的控制路径。
   - **变更感知绕过审查**：不依赖原始理由重新阅读发现和最终差异。从直接调用者追踪更改的分支，检查等效的汇点，并在可行时尝试替代的恶意输入类别。
   - **保留行为**：重新运行合法控制，并确认记录的API、错误语义和兼容性约束保持完整。
   - **仓库检查**：运行聚焦回归测试、所属包的相关测试，以及适用的格式化程序、linter、类型检查器、依赖和集成检查。
   - 在可行时，确认如果移除安全更改，回归检查会失败。
   - 将较早门禁失败视为不合格。仅修订候选更改或返回`blocked`；切勿用样式、更小范围或额外报告来弥补安全关闭或行为保留的失败。
6. 报告结果，包括确切的命令、结果、更改的文件和剩余风险。

## 工作台修复阶段

当Codex安全工作台请求包含扫描ID、出现ID、修复请求ID、操作令牌和预期版本时，仅遵循请求的修复阶段。阶段边界在可能编写代码时改变，但不会削弱上述验证要求。

- **生成**：保持选定的目标检出不变。在需要编辑以开发或测试修复时，使用隔离的工作树或临时副本。应用上述补丁契约和策略门禁，编写一个包含完整源代码和回归测试更改的规范统一差异，然后使用提供的工作台身份记录`generated`或`failed`。
- **应用**：验证记录的基础修订和补丁摘要，然后仅将确切的补丁应用到选定的工作树，不进行无关编辑。记录`applied`或`failed`。在此阶段不验证或关闭发现。
- **验证**：不修改源代码。针对记录的补丁运行上述有序验证门禁。仅当原始问题不再复现、合法行为保持完整且相关仓库检查通过时记录`verified`；在验证摘要中保留确切的命令和结果。否则记录`failed`并说明失败的门禁或证明差距。不关闭发现。

当父线程委托修复阶段时，工作线程通过其终端工作台更新拥有该阶段。父线程仍为编排者，不得重复工作线程的编辑或将聊天响应视为完成。

## 结果和输出契约

在最终响应中，包括：

- 结果：`fixed`、`no_change`或`blocked`
- 具体的脆弱路径、安全不变量和必须保留的合法行为
- 选定的补丁策略及其为何是最窄的完整仓库原生选项，或受阻时未解决的产品决策
- 更改的文件
- 添加的测试或验证产物
- 运行的命令及其通过、失败或未知结果，按有序验证门禁分组
- 明确说明原始问题如何被证明不再复现
- 明确说明合法行为如何被证明保持完整
- 剩余的不确定性或跳过的验证（如果有）

如果使用扫描产物目录，请通过`../../references/scan-artifacts.md`解析它，然后将可见报告写入修复报告路径。如果没有现有的扫描目录，最终聊天摘要就足够了，除非用户要求文件。

## 硬性规则

- 在有序验证门禁全部通过之前，不要报告`fixed`。仅当仓库证据显示检查无关时才省略；不可用的相关检查会使验证`blocked`，必须报告。
- 当聚焦测试或复现器可行时，不要仅依赖代码检查。
- 在没有证据表明更广泛更改是完整关闭所必需的情况下，不要将补丁扩大到无关清理、兄弟发现或架构重新设计。
- 不要移除用户更改或无关的本地修改。
- 不要削弱身份验证、授权、租户隔离、输入验证、沙箱或日志记录以使测试通过。
- 不要隐藏证明差距。如果环境阻止验证，请准确说明哪个命令或设置失败以及仍缺少哪些证据。
