# 静态发现评估

当 Codex Security 工作流需要静态仓库证据来支持或反驳所提供的安全声明时，请使用此参考。

这不是一个顶层工作流。它不定义输入规范化、面向用户的裁决、扫描台账、动态验证或修复行为。这些契约由调用技能负责。

## 评估元组

对于每项声明，确定最小的有用元组：

- 来源：声明中提到的攻击者控制的输入、外部触发器或受信任的操作员输入
- 控制：相关的防护措施、验证器、清理器、授权检查、配置门控、功能开关或缺失的安全控制
- 汇点：危险操作、易受攻击的依赖项、失效的控制或影响点
- 可达路径：在既定前置条件下连接来源、控制和汇点的代码/配置路径
- 边界：使路径具有安全相关性的产品表面和信任边界
- 反证：削弱、推翻或限定声明范围的静态事实
- 证明缺口：阻碍得出更强结论的缺失事实

不要将依赖项存在、字符串匹配或部分调用链视为完整评估。有用的静态评估既要说明发现了什么，也要说明哪些仍未得到证实。

## 证据搜索顺序

在扩大范围之前，先检查最小的相关证据集：

1. 用户提供的位置、扫描器位置、公告参考或 SARIF 结果位置。
2. 依赖清单、锁文件、包导出、二进制入口点、构建元数据、部署配置和生成产物的边界。
3. 受影响的函数、调用点、路由、RPC 处理器、解析器入口点、CLI 命令、插件钩子、消息消费者和包 API。
4. 附近的防护措施、验证器、清理器、授权检查、功能开关、配置检查和补偿控制。
5. 产品表面证据，如 `SECURITY.md`、受支持版本文档、披露政策、威胁模型、产品文档、部署文件、注释和测试，以阐明预期行为。

优先使用精确的仓库引用，而非宽泛的声明。如果证据缺失，请将缺失记录为证明缺口，除非缺失本身推翻了声明。

## 边界和表面检查

在将静态路径视为安全相关之前，请进行分类：

- 产品表面：托管服务、库 API、CLI、本地开发者 UI、MCP/工具表面、插件钩子、示例/演示、测试/夹具、文档、生成代码、供应商代码或未知
- 来源信任：不受信任的用户输入、租户/用户控制的数据、远程攻击者输入、受信任的操作员输入、受信任的开发者配置、仅限本地的输入、有意执行代码的扩展点或未知
- 政策依据：仓库政策、产品文档、部署/配置证据、包元数据、代码注释、威胁模型或未知

检查不受信任的输入是否能够到达缺陷点。

## 静态置信度

根据证据质量校准置信度：

- 高：精确的来源/控制/汇点路径、明确的前置条件、相关的边界证据，且没有实质性未解决的反证
- 中：有一定直接证据的合理路径，但调用链、配置、版本、部署或边界证据不完整
- 低：静态支持薄弱或间接，存在重大歧义，或缺少仓库上下文

使用证明缺口来替代缺失的运行时、环境、政策或部署事实，而不是自行填补。

## 输出要素

调用技能决定最终的 Schema 和标签。静态评估应提供足够的要素供该输出使用：

- 简洁的理由说明
- 来源、控制、汇点和可达路径（如已确定）
- 受影响位置，尽可能包含精确的仓库路径和行号引用
- 边界评估和政策依据
- 支持证据
- 反证
- 证明缺口
- 基于静态证据质量的置信度
- 当静态证据无法解决声明时，给出最小化的下一步操作
