# 最终报告与 Codex 审查指令

在编写规范报告语义并返回生成的 Codex 安全报告和审查指令时，请遵循本指南。

## 最终输出

最终可读输出是 `scan-manifest.json`、`findings.json` 和 `coverage.json` 的确定性投影：

- 主要可读 Markdown 报告位于 `scan-artifacts.md` 中指定的最终扫描报告路径
- 可选的详细漏洞说明位于 `findings/<slug>/` 下，通过 `finding.writeup.reportPath` 从主报告链接
- 可选的结构性加固指南位于 `hardening/` 下，通过 `scan.hardening.portfolioPath` 从主报告链接

在编写此可读输出旁边的 `findings.json` 时，请根据相同的已验证证据填充 `finding-detail-fields.md` 中的可选结构化细节。不要将渲染后的报告解析回发现数据。

使用 `report.md` 作为主要可读入口点。在报告本身中解释与报告相关的工件路径，尤其是在 `Scope`、`Reviewed Surfaces` 和 `Open Questions And Follow Up` 中。

在最终响应中，将生成的 Markdown 报告路径链接为主要可读工件。

每种扫描模式都使用相同的最终报告流水线。Workbench 拥有的 Standard 和 Workbench 支持的 diff 扫描通过 `record_codex_security_scan_draft({ scanId, handoffClaimToken?, scope?, threatModel?, findings, coverage })` 提交规范语义；Workbench 提供权威元数据并写入未密封的规范草稿。Deep Standard 扫描工作线程通过其绑定的草稿工具提交完整的语义结果，协调器聚合这些结果并写入父扫描的未密封规范草稿。SDK 拥有的 Standard 扫描则使用 SDK 提供的精确元数据写入未密封的规范文件，并将最终确定留给 SDK。没有 `scanId` 的终端扫描保留其现有的规范 JSON 工作流。任何模式都不会将现有的 `report.md` 作为输入进行编写、修复或处理。最终确定会验证并丰富规范 JSON，密封规范 JSON 和证据工件，然后确定性地生成 `report.md`。通过结构化的规范语义提供报告文本，而不是单独编写的报告。

对于每个发现，提供一个有证据支持的小写漏洞族 `ruleId`；使用其精确的已知 CWE 提供 `taxonomy: { category, cwe }`；验证位置；以及 `provenance.source`，仅当此插件实际发现该发现时才使用 `"local_plugin"`。在发现扩展中保留真实的工作线程或来源出处以及任何现有的规范候选身份。没有已知 CWE 的发现保留 `cwe: []`；切勿编造分类。仅当其实际代码非空且引用的每个证据 ID 都存在时，才包含可选的 `codeEvidence`。

提供语义覆盖率作为 `{ completeness, surfaces, explicitExclusions, deferred }`，每个表面使用实际的 `label` 和一个现有的 `disposition`。当存在延迟项或 `needs_follow_up` 表面时，将覆盖率标记为 `partial`；保留其真实原因和支持上下文。每个延迟项都需要一个有意义的原因；保留任何现有的 `id` 或 `candidateId`。Workbench 从其候选身份或稳定的延迟工作细节中派生缺失的 ID。开放问题可以是非空字符串或 `{ question, followUpPrompt? }` 对象。Workbench 派生目标和范围元数据、范围包含和排除路径、覆盖率模式和清单策略、发现身份和指纹以及表面 ID。不要将这些 Workbench 拥有的值或顶级覆盖率收据引用放入语义草稿中。

在 Workbench 拥有的 Standard 或 Workbench 支持的 diff 草稿被接受后，或 Deep 协调器返回其父扫描的规范清单后，调用 `complete_codex_security_scan({ scanId, handoffClaimToken? })` 并使用其返回的完成元数据。SDK 拥有的扫描返回其未密封的规范文件，而无需调用完成工具或最终确定器；SDK 拥有完成和报告生成。仅在明确请求时才读取完整的规范结果。对于没有 `scanId` 或完成工具的终端/聊天工作流，在写入规范 JSON 后保留 `python <plugin_dir>/scripts/finalize_scan_contract.py --scan-dir <scan_dir> --source-root <repo_root>`。在 SDK 路径之外，在最终确定成功且生成的报告存在之前，不要将扫描目标标记为完成。

在 `complete_codex_security_scan` 成功后，当 `usage.coverage` 为 `complete` 或 `partial` 时，在其最终响应中包含返回的 `usage.totalTokens`、`usage.inputTokens` 和 `usage.cachedInputTokens`；明确标记部分测量。如果覆盖率为 `unavailable`，则说明无法测量令牌使用量，而不是报告为零或估算成本。在终端/聊天主机中仅报告测量的完成元数据。令牌使用量是 Workbench 元数据，不是修改密封扫描工件或确定性报告的理由。

在 Workbench 拥有的 Standard 或 Workbench 支持的 diff 完成之前，要求 `record_codex_security_scan_draft` 成功。在 Deep 完成之前，要求协调器返回父扫描的已编写规范清单；不要提交另一个草稿或重新运行工作线程阶段。SDK 拥有的 Standard 和终端 diff 工作流则在其相应所有者最终确定之前验证其规范 JSON。完成会验证并密封现有的规范工件并生成 `report.md`；它不会创建缺失的工件或运行跳过的扫描阶段。

MCP `-32602` 输入拒绝、报告 `Input validation error` 的 `isError: true` 结果，或在写入前明确拒绝包含延迟工作或后续表面的完整覆盖率，都不会进行草稿写入。仅纠正同一草稿中指定的路径，保留所有有效的发现、字段、证据和延迟工作；最多重试同一扫描两次。在第一个被接受的草稿后停止。不要盲目重试模糊的传输或写入失败。

对于任何其他必需的扫描阶段、规范工件写入或磁盘存在性检查在完成前失败，停止当前响应并明确指出确切的工作流阻塞因素。不要使用缺失的工件调用完成，返回最终报告或无发现结果，或满足结构化输出模式。保留持久扫描以供后续继续，而不是仅仅因为规范组装受阻而取消或使其失败。

如果 `complete_codex_security_scan` 或终端/聊天最终确定器失败，停止当前响应并明确指出确切的 MCP 或最终确定器错误。不要在同一个响应中重试完成，返回最终报告或无发现结果，或满足结构化输出模式。保留持久扫描以供后续继续，而不是仅仅因为完成失败而取消或使其失败。

规范报告语义存在于以下字段中：

- `scan-manifest.json`：`scan.scope` 和 `scan.threatModel`
- `findings.json`：每个发现的 `summary`、`codeEvidence`、`rootCause`、`validation`、`attackPath.dataflow`、`attackPath.reachability`、`severity.rationale`、`severity.changeConditions`、`remediation`、`remediationTests` 和 `preventiveControls`
- `findings.json`：可选的 `writeup.reportPath`，用于在 `findings/<slug>/<slug>.md` 下编写的派生、未密封的详细漏洞报告
- `scan-manifest.json`：可选的 `scan.hardening.portfolioPath`，用于 `hardening/hardening.md` 处的派生、未密封的设计组合
- `coverage.json`：`surfaces` 包括 `riskArea` 和 `notes`，以及 `openQuestions`

对于整个仓库的 Deep 扫描，Workbench 在存储的覆盖率文档中派生 `coverage.inventoryStrategy: "repository"`；重复发现是工作流元数据，而不是不同的清单策略。不要在 `record_codex_security_scan_draft` 中包含 `inventoryStrategy`。

较旧的 v1 生产者可能会省略新的可选字段。在这种情况下，最终确定使用显式的 JSON 派生回退文本；它永远不会读取预先存在的报告来填补空白。

当存在 `scan.hardening.portfolioPath` 时，包含一个简短的 `## Structural Hardening` 部分，链接到该组合。将单个提案链接和完整的选项分析保留在 `hardening/hardening.md` 中，而不是复制到主扫描报告中。该组合是设计指南，不是任何发现已被修复的证据。

当没有可报告的发现时，包含一个简短的 `No findings` 部分，解释为什么没有发现通过发现或后续的可报告性门控。对于具有覆盖率账本的仓库范围和限定路径扫描，仍然包含 `Reviewed Surfaces`，以便已检查、拒绝、不适用和需要后续跟进的表面保持可审计性。

当存在可报告的发现时，将它们渲染为可读的 Markdown 发现，而不是原始 JSON 或转储的模式对象。
按严重性从高到低对发现进行排序：`critical`，然后 `high`，然后 `medium`，然后 `low`。

仅当观察结果共享相同的受损安全控制和有效修复时才进行分组。保留每个受影响的路径、操作、接收器和支持源位置；即使它们共享一个 CWE，也要保持不同的安全故障分开。

根据主要受损控制设置发现类别和 CWE。不要仅仅因为次要影响使利用更严重，就将次要的支持影响 CWE（如数据暴露或缺少身份验证）添加到注入/RCE/路径/文件/解析器发现中；在文本中提及这些影响，或者如果该次要控制独立易受攻击，则发出单独的发现。

Workbench 拥有的 Standard 扫描直接通过 `record_codex_security_scan_draft` 提交其源支持的最终发现和覆盖率；SDK 拥有的 Standard 扫描将相同的语义写入未密封的规范文件。Deep 扫描在语义上聚合完整的 Standard 工作线程结果，保留验证的发现、攻击路径分析、受影响位置、威胁模型上下文和诚实的覆盖率。协调器编写父扫描的规范草稿；父扫描不读取候选账本、运行单独的验证或攻击路径阶段，或提交另一个草稿。规范 `severity.changeConditions` 必须是一个非空字符串；当 `attack_path.change_conditions` 包含多个字符串时，在写入 `findings.json` 之前将它们合并为一个文本字符串。

对于 Workbench 支持的 diff 候选，按以下顺序应用行结果：验证处置 `reportable` 加上攻击路径决策 `reportable` 成为具有其不同实例和所有相关入口点、根控制、接收器和支持位置的发现；否则，任一阶段的 `deferred` 结果成为 `needs_follow_up` 覆盖率和 `coverage.deferred` 条目，使用记录的的不确定性或证明差距；否则，验证处置 `not_applicable` 成为 `not_applicable` 覆盖率；否则，验证处置 `suppressed` 或攻击路径决策 `ignore` 成为 `rejected` 覆盖率。缺少必需的阶段记录会使候选未解决并阻止完整覆盖率。不需要阶段收据、每个候选的说明或另一次对账过程。

没有 `scanId` 的终端 diff 扫描可以提供每个候选的账本、验证关闭表和仓库覆盖率账本。当这些工件存在时，保留其可追溯性：从可报告/幸存的行开始，保留确切的受影响位置，并将抑制、不适用或延迟的行映射到面向公众的覆盖率结果。不要因为同族的邻居幸存而静默丢弃种子行。

## 报告结构

使用此报告结构：

`# 安全审查：<仓库或目标名称>`

`## 范围`

使用范围内的上下文、审查的工件、运行时或测试状态、验证模式和显式限制填充 `scan.scope`。包含/排除路径和覆盖率字段提供剩余的投影范围内容。如果威胁模型是在阶段 1 期间生成的，而不是由用户提供的，请在规范范围上下文中说明。不要将生成的威胁模型材料称为外部输入。

在范围项目符号之后，当扫描有发现或仓库范围覆盖率时，包含一个紧凑的 `### 扫描摘要` 表。使用列 `字段` 和 `值`。在已知时包含可报告发现的数量、严重性组合、置信度组合、覆盖率和验证模式。将此表下方的工件路径保留。

`## 威胁模型`

当存在完整的规范 `threatModel` 时使用它。在任何仅生成 `<context_dir>/threat_model.md` 的工作流中，包括 Workbench 支持的 diff 扫描，将该文本精确保留为 `{ "summary": "<完成的模型文本>" }` 并将其包含在规范草稿中。在构建生成的规范模型时，使用 `threat-model.md` 中的字段映射和场景对账；不要从最终发现列表重新生成它。保留来源引用、能力边界、部署假设和重要的未知数。最终确定在投影此部分时仅读取规范威胁模型对象。

`## 发现`

从发现摘要表开始此部分。

对于 Deep 安全扫描输出，按 `extensions.candidateId` 分组摘要表，并使用列 `发现`、`报告`、`严重性`、`置信度` 和 `详细说明`。`deep_repository` 扫描始终使用此呈现方式。当可报告的子发现携带下述的深度扫描标识符时，限定路径的深度输出使用它；普通的限定路径标准扫描保持标准表。每个可报告的规范 DSS 发现发出一行表。`发现` 包含漏洞标题，不包含重复的尾部报告或出处注释。`报告` 列出每个子发现的唯一 `extensions.reportId`，每个 ID 链接到该子发现的详细摘要部分。为了与较旧的深度扫描工件兼容，回退到 `extensions.ledgerRowId`；当账本行产生多个报告时，使用每个子发现的唯一尾部标题注释或实例身份，而不是显示重复的标签。`详细说明` 列出每个子报告的相应 `writeup.reportPath` 链接。将每个子报告保留为分组表下方的自己的详细部分。当子报告具有不同的严重性或置信度级别时，在分组行中列出每个不同的级别。在扫描摘要中，区分可报告的 DSS 发现数量与子报告实例数量。对于所有其他扫描模式，保留标准列 `发现`、`严重性`、`置信度` 和 `详细说明`，发现标题链接到详细摘要部分。

在摘要表之后，包含一个紧凑的 `### 置信度标度` 表，列 `标签` 和 `含义`：

- `高`：直接的源代码、配置或运行时证据支持该发现，没有重大的未解决的可达性或可利用性障碍。
- `中`：源代码证据支持一个合理的问题，但运行时行为、部署配置、角色可达性、类型约束或利用可靠性仍需要证明。
- `低`：证据薄弱或不完整；仅当用户明确希望在最终报告中包含后续候选时才包含。

当发现记录 `writeup.reportPath` 时，从发现摘要链接详细报告，不要内联重复完整的发现。链接的说明是派生的、未密封的可读输出；规范发现仍然是适配器和重新生成的事实来源。没有说明的发现继续使用下面的内联格式以保持兼容性。

将每个内联发现渲染为：

`### [<编号>] <标题>`

对于每个发现，在标题正下方包含一个紧凑的两列元数据表。使用列 `字段` 和 `值`。包含以下行：

- `严重性`：`critical|high|medium|low`
- `置信度`：`high|medium|low` 或简短的校准置信度标签
- `置信度理由`：一句话解释为什么置信度标签如此校准，基于验证方法、直接证据和任何缺失的证明
- `类别`：具体的漏洞类
- `CWE`：ID 和名称列表，或 `none`
- `受影响行`：路径：行范围列表

使用具体的类别，如 `授权绕过 / IDOR`、`路径遍历`、`SQL 注入`、`XXE`、`开放重定向` 或 `硬编码凭据`。不要使用通用的占位符，如 `安全扫描发现`。

对于标准扫描模式，摘要表应使用文档内 Markdown 锚点将每个发现标题链接到其详细发现部分。对于 Deep 安全扫描分组呈现，`报告` 列中的报告 ID 拥有该链接。保持显示的漏洞标题和报告 ID 与相应的详细标题对齐。使用确定性投影发出的显式发现锚点。
摘要表和详细发现部分必须使用相同的降序严重性顺序：所有 `critical` 发现在前，然后是 `high`，然后是 `medium`，然后是 `low`。排序后重新编号发现，以便表顺序、详细标题和锚点匹配。

受影响行必须包括根受损控制或危险接收器行（当该行可识别时），而不仅仅是使其可到达的公共包装器、路由或调用者。对于包装器到共享助手的发现，列出可到达的包装器/入口点和底层解析器、反序列化器、路径/归档助手、表达式求值器或认证/授权控制行。如果种子文件、类、包或代码块共享幸存的证明元组，则将该种子锚点保留在受影响行中，而不是用更广泛的仅兄弟位置替换它。如果错误是由接收器之前的不安全转换或选择引起的，则包括控制失败的分割、解析、规范化、标准化、比较、正则表达式、对象选择或对象绑定行。对于解析器、XML、反序列化和对象构造发现，包括具体的编解码器、转换器、反序列化器、解析器功能设置、解析器、类过滤器或容器处理程序行，当该行执行递归解析、类型解析、对象转换、类过滤或故障开放加固时。对于中央文件格式对象模型，包括低级助手行，如 `to*Array`、`toList`、`getObject`、数字转换、迭代器、基于大小的分配、未检查的转换或集合到数组的循环，当这些助手是损坏的格式错误输入控制时。对于递归占位符/模板发现，包括启用递归扩展或表达式求值的助手/解析器设置行，而不仅仅是后面的解析器或渲染调用。对于资源服务发现，包括决定攻击者选择的资源是否被允许的允许列表、路径匹配器、URL 解码、规范化或资源选择行。对于有状态认证协议发现，包括创建认证绕过的主体/凭据/令牌/颁发者安装、重新绑定/重新认证或验证与消费对象选择行。对于 SSO/SAML/联合发现，包括确定哪个身份对象被信任的响应/断言选择、签名对象查找、克隆/返回的断言、主体、受众、接收者、目的地、ACS URL 或颁发者绑定行。对于多态或请求选择的管理程序、操作、转换器、过滤器、验证器或策略族，包括在共享接收器/控制之前转换、验证、规范化、选择或重新解释攻击者输入的具体子类/实现行，包括具体类中执行或启用不安全转换的专门助手方法和
